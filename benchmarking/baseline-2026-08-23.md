## Q01 — Supporting a vulnerable customer changing address

**Question:** A vulnerable customer is moving home and finds forms difficult. How should I help them change their address safely, including identity checks, affected accounts, and any escalation?

**Answer** (completed, 15 turns, 95.5s, $0.6672):

No single "vulnerable customer" domain exists; this synthesizes the change-of-address SOP with the bank's vulnerable-customer/accessibility guidance, since the two live in separate documents.

## 1. Choose the right channel first
For someone who "finds forms difficult," steer them away from the phone/email/post self-service routes and toward an **in-person branch visit**. The SOP rates in-person identity verification as **Low risk** (same as online self-service) versus phone/email, which is **Medium risk** and requires the customer to answer security questions, DOB, last 4 digits of account number, mother's maiden name, etc. — exactly the kind of unaided, form-like recall a vulnerable customer may struggle with. Branch staff can also complete the paperwork *with* the customer rather than leaving them to a form.

`branch_operations_training.md` (banking.communications) confirms branches should offer: large-print forms, a quiet/private area for sensitive discussions, hearing loops, and wheelchair access — use these if relevant.

## 2. Identity checks (in-branch)
Per `sop_change_of_address.md` Step 2:
- Check a government-issued ID (passport/driving licence)
- Compare photo to the customer
- Compare ID address to existing records
- Verify the account-holder relationship

If identity **cannot** be verified: do not process the change, request additional verification, document the reason for refusal, and **escalate to a manager if the customer disputes it**.

Communication style (from `branch_operations_training.md`'s "Customer Communication Guidelines" template and its "Vulnerable Customers" section): speak clearly and face the customer, allow extra time, use plain language with no jargon, offer written confirmation, and arrange an interpreter if there's a language barrier. If the customer shows signs of distress/fear when discussing finances (an "Abuse Victim" warning sign) or possible financial abuse, that must be escalated to Compliance separately — see §4.

## 3. Affected accounts and the update sequence
The SOP's process (Steps 3–12) applies regardless of vulnerability status:
1. **Identify all linked accounts** — savings, current, mortgage, cards; note whether it's a joint account.
2. **Collect and validate the new address**; a second staff member should verify the data entry.
3. **Decide address-per-product**: e.g. a mortgage keeps its property address unchanged (locked to the deed) while the personal/statement address updates.
4. **Joint accounts** need written consent from *both* holders before the address changes.
5. **Proof of address**: usually required for international moves, high-risk jurisdictions, or customers with <5 years' history; may be waived for a low-risk domestic move. Accepted tier‑1 documents: utility bill, council‑tax letter, or another bank's statement (≤3 months old).
6. **AML risk assessment / re-screening**, only triggered if the new address is in a sanctioned/high-risk country.
7. **System updates**: core account system, standing orders, direct debits, statement delivery, data warehouse.
8. **Customer notification**: confirmation goes to the *new* address/email, but a copy is also sent to the **old address** — a deliberate fraud check to catch account takeover, not an error.
9. **QA sign-off** before the request is closed (identity, address validation, AML, KYC, systems, notification all checked).

## 4. Escalation
`sop_change_of_address.md`'s "Escalation Triggers" section:
- **To Manager**: customer disputes the change, multiple address changes in a short period, address in a high-risk country, proof of address not received within 30 days, joint holders disagree.
- **To Compliance Head**: AML screening produces a true match, move to a sanctions country, customer flagged medium/high risk, suspected fraud.
- **To Head of Operations**: process blocked >5 business days, technical system issue, conflicting requirements across multiple accounts, or a regulatory query.

The vulnerability-specific escalation instead sits only in `branch_operations_training.md`: **signs of financial abuse must be escalated to Compliance immediately**, and abuse victims should be offered a safe, confidential space. Treat this as a parallel trigger to run alongside the standard address-change escalation triggers above, not a replacement for them.

## Q02 — Repeated standing-order failures

## Domain used
**`banking.sop_guides`**, document **`sop_standing_orders.md`** (FirstUK Bank — Standing Order Processing SOP, v1.0, effective 2026-01-15, currently active/not superseded). No ambiguity — the document is a direct, exact match for the question, so no other domain was needed.

## What to check
Per the SOP's failure scenarios, walk through these common causes with the customer:
- **Insufficient funds** in the source account on the scheduled execution date
- **Invalid recipient account number** (format issue)
- **Recipient account closed**
- **Payee bank system failure** (issue on the receiving bank's side)
- **Duplicate-prevention block** — if a prior attempt already failed, the system may block a repeat

## What happens after a failed attempt
The SOP defines a five-step failure-handling flow:
1. **Detect failure** — the system logs the failed attempt and marks the standing order status as "Failed."
2. **Alert customer** — an email/SMS is sent including the amount, recipient, and failure reason, along with a request for action (e.g., add funds, update payee details).
3. **Retry attempt** — the system retries once, usually within 24 hours. If the retry succeeds, the standing order resumes normally.
4. **Escalation** — if the retry also fails, the standing order is **suspended** and routed to staff for review, who then contact the customer to resolve it.
5. **Resolution** — the customer supplies corrected information if needed, staff update the standing order, and it either resumes or the customer opts to cancel it.

## Customer's options
- **Fix the underlying issue** (top up the account, correct payee/account details) so staff can update the standing order and let it resume.
- **Modify the standing order** — amount, frequency, payee, or end date can be changed via online banking, phone (0800-555-2265), or branch. Note: changing amount, payee, or frequency requires cancelling the existing standing order and creating a new one.
- **Cancel the standing order** — available via online self-service, phone, branch, or mail. Cancellation is **immediate, free, and requires no notice period**; the next scheduled payment is blocked and the customer receives an email confirmation with the standing order ID and cancellation date.

**Provenance:** All facts above come directly from graph chunk text of `sop_standing_orders.md` (domain `banking.sop_guides`), specifically the "Step 5: Standing Order Execution," "Step 6: Modify Standing Order," "Step 7: Cancel Standing Order," and "Step 8: Failed Standing Orders" sections — no other domains or documents were needed to ground this answer.

## Q03 — Stop a direct debit versus a standing order

**Question:** What is the difference between cancelling a direct debit and cancelling a standing order, and when does each cancellation take effect?

**Answer** (completed, 6 turns, 27.2s, $0.2539):

## Answer

**Domain grounding:** `banking.sop_guides` — specifically `sop_direct_debits.md` and `sop_standing_orders.md` (both Active, effective 2026-01-15, not superseded, so current as of today 2026-08-23).

### The mechanism difference
| | Standing Order | Direct Debit |
|---|---|---|
| Who initiates | The customer (tells the bank what/when to pay) | The biller/company (sends the payment instruction) |
| Amount | Fixed | Can vary |
| Consumer protection | Limited | Full Direct Debit Guarantee |

Because of this, **cancelling** the two works differently:

- **Standing Order cancellation**: The customer instructs the bank directly (online, phone, branch, or mail) to cancel. The bank verifies identity, sets the order's status to "Cancelled," and blocks the next scheduled payment. There's no third party to notify.
- **Direct Debit cancellation**: The customer can cancel via *either* the bank (phone/email/branch/online form) *or* the biller (asking them to stop collecting). If the customer cancels through the bank, FirstUK sets the mandate to "Canceled" and sends an automated cancellation message (ARUDD) to the biller. If the biller initiates it instead, the biller submits the cancellation instruction and the bank updates the mandate status. Either way, one side notifies the other.

### When each takes effect
Both SOPs state cancellation is **effective immediately, with no notice period and no fee**:

- Standing Order: "Effective date: Immediately (no notice period)... Next scheduled payment blocked... No Fees... No Notice Required."
- Direct Debit: "Effective Date: Immediate (no notice period required)... Any Pending Payments: Blocked if cancellation before settlement date."

**One internal inconsistency worth flagging**: `sop_direct_debits.md`'s own summary comparison table (near the top of the document) states Direct Debit cancellation takes effect "Anytime, but **5-day notice typical**," which contradicts the document's own detailed cancellation procedure later on, which says cancellation is **immediate with no notice period**. I'm treating the detailed step-by-step process (Step 6: Mandate Cancellation) as authoritative over the summary table, since it's the operative procedure text, but both statements come from the same document and source, so this is a documented internal discrepancy rather than something I resolved with outside data.

**Bottom line**: The core difference isn't *when* cancellation takes effect (both are immediate, free, no-notice) — it's *who you can cancel through*. A standing order can only be cancelled via the bank (you set it up, only you can stop it). A direct debit can be cancelled via the bank *or* the biller, since the biller is the one actually generating the payment instructions.
